# Choose the models that work on a website

Use this when the owner names a writing model, assigns different parts to different models, or asks how a particular model reads a page. Keep the request conversational: infer file and section boundaries from the approved repository. Use `webby-github` for repository access and publication, `webby-create` for the visual direction, and `webby-audit` for page quality and evidence. A chosen writer is a creative contributor; its authorship does not establish that a search service will find, cite, or recommend the result.

## Connect once

The owner chooses which provider accounts, endpoints, and spending limits Webby may use. Configuration and login state are private, outside the site checkout. Run `webby-model-connect init` to create the per-install configuration. Its reported path is the `--config` argument for `webby-model-draft`. On the cloud image it is `/var/lib/plow/models/config.json`. Existing installations may have the programs in this skill directory instead of on `PATH`; use `python3 /var/lib/plow/workspace/skills/webby-model-choice/webby-model-connect` or `webby-model-draft` there, with `WEBBY_MODEL_STATE_DIR=/var/lib/plow/models`. If CLIs were installed under that state directory, prepend `/var/lib/plow/models/runtime/node_modules/.bin` to the command's `PATH`.

Check `webby-model-draft doctor --config CONFIG --provider PROFILE`. A login/key present is not proof that a selected model can run: only a completed real request establishes that. If connection is missing, explain the one-time step for that provider. Codex can use `webby-model-connect login codex`; deliver only its official verification URL and short device code in the owner's direct conversation, then check `status codex`. Reuse an active login attempt. Claude subscription login uses `webby-model-connect login claude` in a private interactive terminal on the machine running Webby. API connections use `webby-model-connect key PROFILE` in that terminal or a configured secret environment variable. Never ask for API keys, OAuth tokens, or callback authorization codes in chat. Never copy this developer machine's login into somebody else's Webby installation.

Use the owner's selected model ID or intentional provider alias. For an unspecified model within a chosen provider, use the saved `default_model`; otherwise resolve an available model appropriate to the request and make that choice clear. Remember an owner-approved default with `webby-model-connect prefer PROFILE MODEL`. A backend may not expose a requested model even when the provider is connected. Report the exact missing connection or unsupported model; do not silently use another provider. The adapters cover Codex CLI, Claude Code CLI, OpenAI, Anthropic, Gemini, and owner-configured HTTPS services implementing the supported OpenAI-compatible API. They cannot call a closed model with no supported interface.

## Assign, draft, and integrate

Read [plans and receipts](references/plans.md) for the actual configuration and plan shape. Build a small plan from the brief, verified business facts, current content, shared voice, and design tokens. Send only the selected page/section and explicitly needed context files. Exclude credentials, unrelated private files, personal chat history, generated bundles, and repository instructions that do not belong in the task. A shared group may request work with existing owner-approved connections and limits; only the owner can add credentials, endpoints, or spending authority.

Assign an explicit file to each job. For sections within the same file, use unique start/end comment markers surrounding the intended content. Keep markers outside the replacement region; add them to the working branch only when needed. No two draft jobs may overlap. For a whole site, enumerate the intended source files and keep shared content/style decisions consistent. Preserve the existing framework and its valid syntax. A reader-review job writes a report instead of changing a file and can inspect either original or proposed content.

Validate the plan before spending: `webby-model-draft validate --config CONFIG --plan PLAN --repo REPO`. Run with `webby-model-draft run --config CONFIG --plan PLAN --repo REPO --output NEW_PRIVATE_DIRECTORY`. These calls generate bounded source proposals; the selected models receive no shell, browser, or repository-editing tools. The original checkout stays unchanged. Use a fresh output directory for each attempt. Direct API jobs have output-token and time limits; CLI jobs have time/output-byte limits and provider-specific controls, with the differences recorded. Read a failed receipt before retrying; completed jobs can have consumed usage even if the entire plan failed. Do not automatically repeat a paid plan or enlarge its limits.

Read the receipt, proposed files, and patch. Confirm the requested provider/model, actual model when reported, complete output, correct section boundaries, and agreement with the owner's facts. Check the assembled page for inconsistent voice, repeated claims, missing transitions, broken component syntax, and visual drift. Review a comprehension result against the supplied facts and its quoted evidence; a model's opinion is not a factual verdict. A supplied-text check does not test public search retrieval, live citations, or actual browser task completion.

Only accept a `review_ready` result. Check the patch against the current source with `git apply --check` before applying it to the approved working branch; if source changed since drafting, reassess the diff rather than forcing it. Run the project's build/checks, the applicable site audit, and rendered review after integration. Open one coherent pull request with a concise model-contribution receipt, evidence, and preview when available. Follow existing owner approval for merge/publish and verify the live result. The user should request the outcome; Webby should handle the plan and integration mechanics.
