# Browser task checks

The artifact parent must exist. In cloud Webby, run `install -d -m 700 /var/lib/plow/models` as the current runtime user and select a new directory beneath it. If `webby-render-check` is absent from `PATH` on an existing installation, invoke `node /var/lib/plow/workspace/skills/webby-model-choice/webby-render-check` with the same arguments.

Choose a task a visitor actually needs: understand the offer, compare plans, find compatibility, locate contact details, or reach the start of signup. Use synthetic data in an approved preview for form testing. On production, stop before sending a message, creating an account, booking, purchasing, or changing data unless that action is explicitly authorized.

When installed, `webby-render-check URL --output /absolute/new/review-directory` captures actual browser screenshots, visible text, accessibility snapshots, layout measurements, and a keyboard-focus sample across phone/tablet/desktop and reduced motion. Use a new artifact directory outside repositories; `--allow-loopback` permits only the exact approved localhost preview origin. Read `manifest.json` and inspect the screenshot images. This helper does not click controls or complete tasks: use its evidence for the checks below and report interactive task execution as unverified when a separate interactive browser is unavailable.

If the current model cannot inspect image pixels, follow the [connected visual review procedure](../../webby-create/references/rendered-review.md#use-a-connected-model-to-inspect-the-screenshots). When no reviewer was selected, prefer Plow's existing configured image capability: `openclaw infer image describe --file SCREENSHOT --model CONFIGURED_VISION_MODEL --prompt REVIEW_TASK --json`. Verify the installed command and available model, use its existing authentication, and check the actual successful image response. Record the screenshot hash, capture context, and requested/reported model with its observations. This avoids a new account setup when the installation already supports image review.

Preserve an owner-selected reviewer; use `webby-model-choice` for that connection, or an approved suitable connected model when native image review is unavailable. Set the read-only capture directory as `--repo`, use `operation: "review"`, supply a `*-text.txt` path, optional `*-accessibility.txt` context, and an `images` array naming actual screenshots from that capture. Keep image hashes, requested/reported model, and image transport from the receipt. Require an accepted image review with `image_access: "viewed"` and observations tied to each attached image and visible location. If the model cannot view images or the request fails, visual review remains unverified; never substitute a text-only visual verdict. Long or truncated pages may need additional focused captures within the runner's image limits. A viewport ending mid-section is normal; compare suspected clipping with the full-page image, capture limits, and DOM before reporting a defect.

A named-model comprehension review may use the text and accessibility snapshot alone, but label it a supplied-text check. Model-reported visual judgments are distinct from measured DOM facts, and neither kind of review proves a browser task completed, that a live search service cited the site, or that a design has an objective quality score.

1. **Read the page three ways.** Compare the visible rendering, DOM, and accessibility tree when available. The same product, facts, actions, and states should be understandable in each. Prefer native links, buttons, inputs, headings, and landmarks. A custom control needs correct semantics and full keyboard behavior, not only a role attribute.
2. **Start from the real entry point.** Navigate through visible controls using accessible names. Do not rescue a broken task with a hidden route, CSS selector, direct API call, or privileged session, then report success. Note any assistance required.
3. **Verify action identity.** Link text should describe its destination; a button should describe its action. Match visible labels with accessible names. Associate every field with its label, instructions, required status, and relevant error. Expose selected, expanded, disabled, and busy states accurately. Keep DOM order consistent with the intended reading and focus order.
4. **Verify progress and completion.** Loading, validation, failure, and success must be recognizable. Preserve input on recoverable errors and provide a clear next step. Associate errors with fields and announce important asynchronous updates. Do not treat a click, spinner, or HTTP request as completed work without checking the visible outcome.
5. **Exercise the interaction.** Check keyboard traversal, visible unobscured focus, menus/dialogs, Escape where appropriate, and return of focus after closing. Test invalid and empty input in a preview when relevant. A harmless read-only route should survive reload/back navigation. Inspect overlays, sticky headers, and cookie banners for blocked controls.
6. **Inspect stability and visual quality.** Check a narrow phone and desktop, plus an intermediate width and 200% zoom for visual changes. Verify readable navigation/body copy, deliberate hierarchy and spacing, adequate contrast and target size, no unintended horizontal overflow, and no clipped labels. Reserve media space to avoid layout shifts; respect reduced-motion preferences. Avoid hover-only routes or moving controls required for completion.

Capture: entry URL, task, browser/device or viewport, authentication state, observed steps, expected outcome, actual outcome, and a screenshot or specific DOM evidence for failures. Describe the tested task precisely; one successful task is not proof of universal agent compatibility or full accessibility conformance.

For sites whose business benefits from explicit agent actions, consider a supported tool interface only after the ordinary UI works. Treat emerging browser protocols as optional and evolving; feature-detect support, preserve the normal interface, validate inputs and permissions on the server, and retain user confirmation for consequential actions. A tool declaration does not prove authorization, security, or actual execution.
