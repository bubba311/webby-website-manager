# Site checks

Apply only the checks relevant to the page and the intended audience. Classify each result by the evidence actually available.

## Access, rendering, and index eligibility

- Check the final URL, redirect chain, HTTP status, and response body together. A `200` login screen, consent wall, security challenge, or empty application shell is not evidence that the main content is available. Compare an anonymous request with the rendered page. Inspect production response headers as well as HTML.
- Read `robots.txt` at the **origin root**, including on hosts that serve the site under a subpath. Evaluate rules for the actual URL path. Separately inspect `noindex`, `nosnippet`, `max-snippet`, and `data-nosnippet`, including crawler-specific directives and `X-Robots-Tag` headers. These controls serve different purposes. Blocking crawling can prevent a crawler from seeing a `noindex` or canonical declaration; it does not reliably remove an already discovered URL.
- Verify crawler policy per service: Googlebot and Bingbot for their search products, OAI-SearchBot for ChatGPT search, Claude-SearchBot for Claude search, and PerplexityBot for Perplexity search. GPTBot, ClaudeBot, and Google-Extended represent different controls; do not open training access as a prerequisite for search. User-requested fetchers such as ChatGPT-User, Claude-User, and Perplexity-User have separate behavior. Recheck the provider's current rules before changing policy.
- A permitted robots rule does not prove requests survive the CDN, firewall, rate limit, or CAPTCHA. If owner logs are available, check verified crawler requests and response status. A claimed user-agent alone does not establish a real provider visit. Preserve security controls; scope any authorized exception to the provider's current identity verification method.
- Check that the primary offer, critical prices/conditions, navigation, and useful answers are available without signing in or performing an interaction to fetch them. Google can render JavaScript; other readers differ. Inspect both response HTML and the rendered DOM instead of declaring all JavaScript unreadable. Content fetched only after a click or scroll needs explicit verification. Offer important information as text, not only in an image, canvas, CSS-generated text, or download. Accessible accordions are fine when their content is present and retrievable.
- Use real links with meaningful destinations and descriptive text. Reach important pages from relevant pages, not only a sitemap. Compare canonical declarations, redirects, internal links, sitemap URLs, and the owner's indexing report for consistency. Canonicals are signals, not guaranteed selections. Never point distinct useful pages at the homepage just to simplify the map.
- Keep sitemaps focused on intended canonical public pages; `lastmod` must reflect substantive changes. Check that relocated URLs reach the right replacement and that removed pages do not masquerade as useful `200` pages. If relevant, review translations, product variants, filters, and pagination for duplicate or inaccessible destinations.
- Actual index state needs the service's inspection/reporting evidence. If the owner supplies Search Console access or exports, check the effective Search generative AI inclusion setting, including inherited parent settings, alongside crawl/index/snippet eligibility. A public HTML audit cannot inspect that account setting. Keep it **verification needed** when unavailable.

## Meaning, answers, and trust

- Make the business/product name, category, audience, outcome, and next action clear in visible copy. Keep names, prices, locations, units, dates, and claims consistent across related pages, metadata, structured data, and any verified owner profiles. Disambiguate similar names with real identifying facts.
- Answer the questions that change a visitor's decision: what it does, who it fits, how it works, requirements, cost when public, limitations, and what happens next. Use a direct answer followed by useful detail, examples, comparisons, or steps where appropriate. Choose paragraph length and headings for comprehension, not a fixed extraction formula.
- Add information only this business can substantiate: a real product demonstration, documented workflow, test methodology and results, original experience, or a concrete case study with permission. Clearly distinguish available features from planned work. Do not convert uncertainty into confident sales copy.
- Place evidence near consequential claims. Verify that a cited source supports the specific statement; retain sample size, date, units, scope, and caveats for measurements. Give author/reviewer context when expertise matters. Update time-sensitive facts when they change; never refresh dates without reviewing the content.
- Match the format to the task: comparison tables for like-for-like attributes, ordered steps for a process, captions/transcripts for informative media, and questions when users actually ask them. Do not generate redundant questions or near-duplicate pages for every wording of a query.
- Use truthful titles and summaries that identify the specific page. Keep essential meaning in readable text while maintaining expressive art direction. Decorative typography or imagery should reinforce the message without carrying facts that disappear from the DOM or accessibility tree.

## Structured data and business-specific checks

- Add structured data only for a real visible entity and an actual consumer or supported search feature. Check syntax **and** type, required properties, relationships, canonical identifiers, URLs, and agreement with current visible content. Parsing JSON alone proves none of those semantic properties.
- Do not fabricate reviews, ratings, stock, offers, organization details, or author credentials. Do not claim a supported schema type guarantees a rich result or an AI citation. Useful FAQ content can stand on its own; adding FAQ markup is not a universal visibility feature.
- For products, reconcile price, currency, availability, variant, shipping, and return details with the actual offer and any approved merchant feed. For local services, reconcile name, service area/address, hours, and contact methods with verified profiles. For documentation, make version, prerequisites, examples, limitations, and stable section links clear. For time-sensitive publishing, show actual authorship and review/update context.
- If a real integration requires a feed, documentation index, action protocol, or notification service, maintain it from the same facts as the visible site and verify the consumer. A discovery notification can speed awareness of changes for participating services; it does not guarantee indexing. Do not add protocol files or publish feeds just to check a box.
